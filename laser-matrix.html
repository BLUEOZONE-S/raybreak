How the machine is addressed

One USB-serial port carries two separate languages. Everything we send to move anything — or to try to fire the laser — is a packet command block in the data part of an SF packet, framed 46 00 … 86.

ASCII console — 19200 8N1, \n\n\n + verb + ;. Only the first two letters are the verb; arguments are comma-separated numbers. Used for status (GS, GP, GQ) and the TS; handshake. Wrong argument count returns "Illegal number of parameters", which proves a verb exists without running it.
SF packet protocol — after the handshake, 460800 baud, CRC-framed. A command block is 46 00 then one or more opcodes then 86. A move is 1A DA <speed> 9E <x> <y>; the laser-flagged move uses 9F instead of 9E. Power/enable opcodes, if they exist, live among the B0–CF block.

Commands that disturb the machine

These each knocked the controller out of its working state — a hang, a dropped move, or the link going silent — and needed a power cycle. They stay on the matrix so we never send them by accident, and so a fix can be checked against them.

What's left, and the leading theory

Still to run: the rest of the alone opcodes at other values, the untried move and pair contexts, writing the laser parameters (4A–4F, DE) then moving, and the opcodes outside the known table (~190 values, highest risk).
Leading theory: when an enable-style opcode precedes a move, the controller silently drops the move instead of firing. That looks like the laser path is gated behind a condition the machine won't meet — most likely the Y axis never finished referencing. If so, the laser may stay dark until the Y card is fixed, and no command will override it.
